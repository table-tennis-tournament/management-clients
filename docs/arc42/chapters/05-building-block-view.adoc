== Building Block View

This chapter describes the building blocks at two C4 levels: the container level (Level 2) and the component level (Level 3).

=== Level 2: Containers

[plantuml, target="container", format="svg"]
----
include::../diagrams/container.puml[]
----

[cols="1,3"]
|===
|Container |Responsibility

|Admin View
|Angular 22 SPA for tournament administration: match assignment, calling, queue management, results.

|Result View
|Angular 22 SPA for displaying live results and standings.

|Table Manager View
|Angular 22 SPA for table-specific match management and result entry.

|Reverse Proxy
|Nginx. Serves the three SPA bundles and proxies API and WebSocket traffic to the backend.

|Backend
|Kotlin 2.4 on Spring Boot 4.1, a modular monolith structured with Spring Modulith. REST API under `/api/v2`, STOMP update events on `/ttt-websocket`, PDF referee sheets and printing.

|Tournament Database
|MariaDB/MySQL in production, H2 in tests. Persists players, matches, tables, groups and settings.
|===

=== Level 3: Backend Modules

The backend is a modular monolith. Each top-level package under `de.ttt.management` is a Spring Modulith module and follows an onion architecture (`domain` → `application` → `infrastructure`).

[plantuml, target="backend-components", format="svg"]
----
include::../diagrams/backend-components.puml[]
----

[cols="1,3"]
|===
|Module |Responsibility

|registration
|Players, clubs, doubles, disciplines and registration state (paid/active/seed). Register/unregister players.

|grouping
|Group standings, computed when the last match of a group is completed. Group formation and seeding stay in mktt. A knockout winner moves on into the next match in `tournament`.

|tournament
|Match lifecycle and state machine, Queue/MatchList, table assignment, results, caller (first/second/third call) and table-manager operations.

|settings
|System settings, printer selection and printing of referee sheets (PDF with a QR code).

|outbound
|The single WebSocket publisher. Consumes domain events after the transaction commits and pushes update events to the five STOMP topics.

|Shared configuration
|Cross-cutting Spring configuration in the root package: `ApiVersionConfig` (the `/api/v2` prefix), `OpenApiConfig` and `ClockAndIdConfig` (the injectable `Clock` and id generator).
|===

Each module internally layers as follows:

[cols="1,3"]
|===
|Layer |Responsibility

|domain
|Aggregates, value objects, match-state enum and repository ports (interfaces only).

|application
|Use-case orchestration, application services, event publication.

|infrastructure.database
|JdbcClient repository adapters (plain SQL, no JPA/Hibernate).

|infrastructure.web
|REST controllers.

|infrastructure.messaging
|Event listeners/publishers.
|===

=== Level 3: Frontend Components

All three SPAs share the same internal structure. The following diagram shows the generic structure; the table below maps the concrete feature modules per application. Three modules under `src/app/shared/` are identical copies in every client that uses them: `update-events` (the STOMP connection, scope filtering, coalescing and resynchronization), `result-entry` (the rules of a Set and a Match) and `match-state` (the questions clients ask about a Match's state).
