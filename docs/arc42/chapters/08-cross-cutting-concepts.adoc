== Cross-cutting Concepts

=== Security

* There is no authentication or authorization: the system runs in the venue's local network, and every client may call every endpoint and subscribe to every topic.
* SQL injection prevention through JdbcClient parameterized queries (prepared statements).
* The domain validates every transition and result (`TournamentMatch`, `SetResult`); a rejected command answers with a 400 and `{"success": false, "message": ...}`.
* Environment-based configuration (database credentials and connection strings are supplied via environment variables).

=== Error Handling

* Controllers translate a rejected command into a 400 with a status body; unexpected errors use Spring's default error response.
* The frontends show German snackbar or toast messages for failed requests; the Table Manager View retries a failed table load and offers a reload.
* STOMP heartbeats every 10 s in both directions detect dead connections; clients reconnect after 5 s and then resynchronize.

=== Logging and Monitoring

* Logging with SLF4J/Logback in the backend.
* Spring Boot Actuator liveness and readiness probes (`/livez`, `/readyz`). Readiness checks the database, mktt's tables, Flyway's migrations and the WebSocket broker, each database check within 2 s. Docker Compose waits on it; nginx serves `/healthz` for itself and proxies `/readyz`, so the whole system's readiness is visible on port 80 (`spec/07_backend_modular_monolith.md`, section 7).
* `deploy/check-ready.sh` checks a running system from outside, including a WebSocket handshake through nginx.

=== Data Consistency

* Database transactions for critical operations (`@Transactional` on application services).
* Each module owns its data; cross-module state is synchronized via domain events.
* Real-time synchronization across all clients via the `outbound` module's WebSocket publisher.
* Automatic recomputation of group standings once a group is completed.

=== Testing

* The backend is tested with JUnit 5 and the Spring Modulith test starter.
* `OnionArchitectureTests` (ArchUnit) enforces the onion layering per module.
* `ApplicationTests` runs `ApplicationModules.verify()` to enforce module boundaries.
* `@ApplicationModuleTest` module tests (with `PublishedEvents`) verify use-case behaviour and endpoint calls in isolation.
* `@SpringBootTest` tests with H2 (MySQL mode) and a STOMP client verify persistence and WebSocket outbound events.
* Tests compare complete results: REST bodies and update events against recorded files in `src/test/resources/expected/` (re-recorded with `-DupdateExpected=true`), database rows, domain events and objects as a whole. Every test builds its own data (`DatabaseHelper`) with a fixed `Clock` and fixed ids.
* Mutation testing (PIT) of the `domain` packages runs on demand.
* The client specs reuse the backend's recorded update events as fixtures.
* All three frontends use Vitest for unit tests (type-checked separately with `npm run test:types`) and Playwright for end-to-end tests that run against the Docker Compose stack.
* CI runs the backend tests and, per frontend, the Prettier check, the spec type check, the unit tests and the end-to-end tests.
