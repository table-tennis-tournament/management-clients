== Solution Strategy

=== Technology Decisions

[cols="1,2,2"]
|===
|Area |Decision |Rationale

|Backend framework
|Scala with Play Framework

|Mature web framework with excellent WebSocket support.

|Frontend framework
|Angular with ngrx

|Component-based architecture and predictable state management.

|Database
|MariaDB/MySQL with Slick

|Relational model fits tournament data; proven reliability.

|Real-time communication
|STOMP over a native WebSocket, no SockJS fallback

|Bi-directional communication; all clients are modern browsers, so no fallback is needed.

|State management
|ngrx (Redux pattern)

|Predictable state, time-travel debugging, single store per application.

|Containerization
|Docker with Docker Compose

|Simplified deployment and consistent environments.

|Documentation rendering
|PlantUML with the C4-PlantUML library

|Text-based, versionable diagrams in a standard notation.
|===

=== Architecture Patterns

* *Separate frontends per role*: three independent Angular applications share one backend.
* *Event-driven real-time communication*: Spring application events are published after commit on five topics and broadcast over STOMP/WebSocket; clients re-fetch the affected state over REST.
* *Layered backend*: controllers, a single data-access component and domain models.
* *Repository-style data access*: one component (Tables) owns all persistence and the in-memory domain state.
* *Redux store*: each frontend keeps its state in a single ngrx store.
