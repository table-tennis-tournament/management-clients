== Runtime View

This chapter describes two important runtime scenarios as C4 dynamic diagrams.

=== Assign a Match to a Table

[plantuml, target="dynamic-assign", format="svg"]
----
include::../diagrams/dynamic-assign.puml[]
----

The Tournament Administrator selects a match and a table. The `tournament` module's controller delegates to its application service; the `TournamentMatch` aggregate validates the transition, a JdbcClient repository persists it and the service publishes `MatchAssigned`. After the commit the `outbound` module sends a `MATCH_ASSIGNED` update event on `/topic/matches`, naming the match, its discipline and the table. Every client whose view the event concerns re-fetches that state over REST, so the Table Manager View of that table shows the match immediately.

=== Enter a Match Result

[plantuml, target="dynamic-result", format="svg"]
----
include::../diagrams/dynamic-result.puml[]
----

The Table Manager enters the set and match results. The `TournamentMatch` aggregate validates them (a Side wins three Sets), the match becomes `Completed` and leaves its table, and the service publishes `MatchCompleted`. The `grouping` module recomputes the group standings when the group's last match is completed. After the commit `outbound` sends a `MATCH_COMPLETED` update event; the Result View reloads the displayed discipline if the event names it, the Admin View and the Table Manager View reload their tables. Writing the winner into the next knockout match is not migrated from the legacy backend yet.

=== Real-time Communication

Real-time updates flow through the `outbound` module, the only component with a WebSocket dependency. Application services in other modules publish Spring application events; after the transaction commits, `outbound` listens (`@TransactionalEventListener`) and pushes a thin JSON event to the matching topic (`/topic/matches`, `/topic/tables`, `/topic/queue`, `/topic/players` or `/topic/settings`) via `SimpMessagingTemplate`. Each SPA receives the events over its STOMP connection, ignores events whose scope does not concern its view, and re-fetches the affected state over REST into its ngrx store. After every (re)connect the SPA reloads the state it displays.
